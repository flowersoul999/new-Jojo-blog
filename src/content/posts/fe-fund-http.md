## 一、HTTP是什么？网络通信的普通话

### 1.1 一句话理解HTTP

**HTTP就是浏览器和服务器之间说话的"普通话"——大家都遵守这个规则，才能互相听得懂。**

HTTP = HyperText Transfer Protocol（超文本传输协议）。名字听起来很高大上，其实就是一个约定——浏览器和服务器约定好，你这么说我这么回，大家都按这个格式来，就能互相通信了。

就像中国人说中文，美国人说英文，大家都讲普通话才能交流。HTTP就是互联网上的"普通话"。

### 1.2 生活中的比喻

用"点餐"来比喻HTTP再合适不过了：

| HTTP角色 | 生活比喻 | 说明 |
|----------|----------|------|
| 浏览器 | 顾客 | 想吃东西了，下订单 |
| 服务器 | 餐厅后厨 | 收到订单，做好了送出来 |
| HTTP协议 | 点餐流程 | 怎么点、怎么送、怎么说 |
| URL | 菜单编号 | 你要吃哪道菜 |
| 请求方法 | 操作类型 | 点菜/加菜/退菜 |
| 状态码 | 结果反馈 | 做好了/卖完了/做错了 |

完整流程大概是这样的：
1. 顾客（浏览器）说："我要一份宫保鸡丁（GET /food/gongbaojiding）"
2. 后厨（服务器）收到订单，做好菜
3. 后厨说："好嘞，这是您的宫保鸡丁（200 OK）"
4. 顾客吃到了菜（页面渲染出来）

是不是一下子就懂了？

### 1.3 HTTP在网络中的位置

网络通信是分层的，从下到上大概是：

```
┌─────────────────────────────┐
│   应用层（HTTP、FTP、SMTP）  │ ← 我们写代码主要在这层
├─────────────────────────────┤
│   传输层（TCP、UDP）         │ ← 管传输可靠
├─────────────────────────────┤
│   网络层（IP）               │ ← 管路由寻址
├─────────────────────────────┤
│   数据链路层 + 物理层        │ ← 管物理传输
└─────────────────────────────┘
```

HTTP属于**应用层协议**，建立在TCP协议之上。简单说：
- TCP管"数据能不能安全送到"（不丢包、不损坏、顺序对）
- HTTP管"送的是什么内容，怎么解读"（用什么格式、什么编码）

你可以这么理解：
- TCP = 快递公司，保证包裹安全送达
- HTTP = 包裹里的信，规定了信的格式（开头怎么写、正文怎么写、结尾怎么写）

## 二、一次完整的HTTP请求：浏览器都干了啥？

面试经典题：**从输入URL到页面显示，发生了什么？**

这道题能把整个前端的知识体系串起来。我们一步步拆解。

### 2.1 输入URL到页面显示

完整流程可以分成这几步：

```
1. 输入URL → 2. DNS解析 → 3. TCP连接（三次握手） → 4. 发送HTTP请求
→ 5. 服务器处理 → 6. 返回HTTP响应 → 7. 浏览器解析渲染 → 8. 关闭连接
```

我们一步步说。

### 2.2 DNS解析

你输入的是 `www.baidu.com`，但网络世界里机器只认IP地址（比如 `180.101.50.242`）。DNS就是"互联网的电话簿"——把域名翻译成IP地址。

DNS解析过程（递归查询）：
1. **浏览器缓存** → 浏览器之前访问过吗？有就直接用
2. **操作系统缓存** → 系统里有没有记录？
3. **本地DNS服务器** → 你家路由器/运营商的DNS
4. **根DNS服务器** → 问.com的服务器在哪
5. **顶级域DNS（.com）** → 问baidu.com的服务器在哪
6. **权威DNS服务器** → 告诉你www.baidu.com的IP是多少

💡 **小知识**：DNS解析结果会被层层缓存，所以第二次访问会快很多。

### 2.3 TCP连接（三次握手）

拿到IP了，浏览器要跟服务器建立TCP连接。为什么要三次握手？一句话：**确保双方都能发也能收。**

用打电话比喻：
```
客户端：喂，能听到吗？（第一次）
服务端：能听到，你能听到我吗？（第二次）
客户端：也能听到，那我们开始聊吧！（第三次）
```

对应到TCP：
1. 客户端发 SYN 包 → 我要连接
2. 服务端回 SYN+ACK 包 → 收到了，我也准备好了
3. 客户端发 ACK 包 → 好的，开始传数据

为什么不是两次？因为两次只能确认客户端能发、服务端能收，没法确认服务端能发、客户端能收。三次就都确认了。

### 2.4 发送HTTP请求

连接建立了，浏览器就开始发HTTP请求了——请求行、请求头、空行、请求体，具体结构我们第三节说。

### 2.5 服务器处理响应

服务器收到请求，交给后端程序处理（比如Node.js、Java、Python），然后返回HTTP响应——状态行、响应头、空行、响应体。

### 2.6 浏览器渲染页面

浏览器拿到响应后：
1. 解析HTML，生成DOM树
2. 解析CSS，生成CSSOM树
3. 合并成渲染树（Render Tree）
4. 布局（Layout）：计算每个元素的位置和大小
5. 绘制（Paint）：把像素画到屏幕上
6. 合成（Composite）：把多个层合成显示

如果遇到 `<script>` 标签，会暂停渲染，先下载执行JS（因为JS可能会改DOM）。这也是为什么建议把script放在body底部或者加async/defer。

## 三、HTTP请求报文：浏览器说了啥？

HTTP请求报文，就是浏览器发给服务器的"一封信"，有固定的格式。

### 3.1 请求报文结构

```
请求行 →  GET /api/users?page=1 HTTP/1.1
请求头 →  Host: api.example.com
         User-Agent: Chrome/120.0.0.0
         Accept: application/json
         Content-Type: application/json
         ...（还有很多）
空行 →   （一个空行，分隔头和体）
请求体 →  {"name": "小明", "age": 18}
```

四个部分：**请求行、请求头、空行、请求体**。

空行很重要——它告诉服务器，头说完了，接下来是正文。

### 3.2 请求方法：GET/POST/PUT/DELETE

请求方法就是"你要干什么"，常见的有这几个：

| 方法 | 作用 | 类比 | 有请求体吗 |
|------|------|------|-----------|
| **GET** | 获取数据 | 查/点菜 | 一般没有 |
| **POST** | 提交数据（新增） | 增/下单 | 有 |
| **PUT** | 更新数据（全量） | 改/换一道菜 | 有 |
| **PATCH** | 更新数据（部分） | 改/加辣 | 有 |
| **DELETE** | 删除数据 | 删/退菜 | 一般没有 |
| HEAD | 获取响应头 | 问价格 | 没有 |
| OPTIONS | 查询支持的方法 | 问菜单 | 没有 |

这就是 **RESTful API** 的设计风格——用不同的HTTP方法表示不同的操作，URL表示资源。

```
GET    /users       获取用户列表
GET    /users/1     获取id为1的用户
POST   /users       新增用户
PUT    /users/1     全量更新id为1的用户
PATCH  /users/1     部分更新id为1的用户
DELETE /users/1     删除id为1的用户
```

### 3.3 请求头：浏览器的悄悄话

请求头就是浏览器发给服务器的"附加信息"，用key-value的形式。

最常见的请求头：

| 请求头 | 作用 | 例子 |
|--------|------|------|
| `Host` | 请求的主机名 | `api.example.com` |
| `User-Agent` | 浏览器信息 | `Mozilla/5.0 Chrome/120` |
| `Accept` | 能接受什么类型的响应 | `application/json` |
| `Accept-Language` | 接受的语言 | `zh-CN,zh;q=0.9` |
| `Accept-Encoding` | 接受的压缩方式 | `gzip, deflate, br` |
| `Content-Type` | 请求体的类型 | `application/json` |
| `Content-Length` | 请求体大小 | `256` |
| `Cookie` | 携带的Cookie | `token=xxx; userId=1` |
| `Authorization` | 认证信息 | `Bearer xxxxxx` |
| `Referer` | 从哪个页面来的 | `https://example.com/` |
| `Cache-Control` | 缓存控制 | `max-age=0` |

这些头信息服务器都能拿到，然后根据这些信息做不同的处理。

💡 **Content-Type常见值**：
- `application/json` → JSON格式（最常用）
- `application/x-www-form-urlencoded` → 表单格式（默认）
- `multipart/form-data` → 文件上传
- `text/plain` → 纯文本

### 3.4 请求体：带过去的数据

请求体就是"正儿八经的数据"，比如你提交的表单、上传的JSON等。

GET请求一般没有请求体（参数放URL里），POST/PUT/PATCH有请求体。

举个登录请求的例子：

```
POST /api/login HTTP/1.1
Host: api.example.com
Content-Type: application/json
Content-Length: 45

{"username": "admin", "password": "123456"}
```

## 四、HTTP响应报文：服务器回了啥？

服务器收到请求后，会返回一个响应报文，格式跟请求很像。

### 4.1 响应报文结构

```
状态行 →  HTTP/1.1 200 OK
响应头 →  Content-Type: application/json
         Content-Length: 1024
         Set-Cookie: token=xxx
         Cache-Control: max-age=3600
         ...
空行 →   （一个空行）
响应体 →  {"code": 0, "data": {...}, "msg": "success"}
```

也是四个部分：**状态行、响应头、空行、响应体**。

### 4.2 状态码：服务器的暗号

状态码是三位数字，告诉你请求的结果怎么样。分五类：

| 分类 | 含义 | 常见的 |
|------|------|--------|
| **1xx** | 信息性状态码 | 100、101（不常用） |
| **2xx** | 成功 | 200、201、204 |
| **3xx** | 重定向 | 301、302、304 |
| **4xx** | 客户端错误 | 400、401、403、404 |
| **5xx** | 服务端错误 | 500、502、503、504 |

详细的后面专门说。

### 4.3 响应头：服务器的回复说明

常见响应头：

| 响应头 | 作用 | 例子 |
|--------|------|------|
| `Content-Type` | 响应体的类型 | `application/json; charset=utf-8` |
| `Content-Length` | 响应体大小 | `1024` |
| `Content-Encoding` | 压缩方式 | `gzip` |
| `Set-Cookie` | 设置Cookie | `token=xxx; Path=/; HttpOnly` |
| `Cache-Control` | 缓存控制 | `max-age=3600` |
| `ETag` | 资源标识 | `"abc123"` |
| `Last-Modified` | 最后修改时间 | `Wed, 21 Oct 2023 07:28:00 GMT` |
| `Location` | 重定向地址 | `https://example.com/new` |
| `Access-Control-Allow-Origin` | 跨域允许 | `*` 或具体域名 |
| `Server` | 服务器信息 | `nginx/1.20.1` |

### 4.4 响应体：返回的数据

响应体就是服务器返回的"干货"——可能是HTML、JSON、图片、视频……

如果是接口请求，响应体一般是JSON：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "id": 1,
    "username": "admin",
    "avatar": "https://..."
  }
}
```

如果是网页请求，响应体就是HTML代码，浏览器拿到后解析渲染。

## 五、GET vs POST：到底有啥区别？

面试必考题！网上很多说法都不准确，我们来彻底搞清楚。

### 5.1 常见区别

| 区别点 | GET | POST |
|--------|-----|------|
| 作用 | 获取数据 | 提交/新增数据 |
| 参数位置 | URL后面（?key=value） | 请求体里 |
| 参数长度 | 浏览器对URL长度有限制 | 理论上无限制 |
| 安全性 | 参数在URL里，明文可见 | 相对安全（也不是绝对安全） |
| 可缓存 | 可以被缓存 | 一般不缓存 |
| 可收藏为书签 | 可以 | 不行 |
| 后退/刷新 | 无害 | 会重新提交表单 |
| 幂等性 | 幂等（请求多少次结果一样） | 不幂等（提交多次创建多条） |

这些都是表面区别，根本区别是什么？

### 5.2 深层理解

**根本区别是语义不同**：
- GET是**幂等**的——读操作，请求多少次结果都一样，不会改变服务器数据
- POST是**非幂等**的——写操作，每次提交都可能改变服务器状态

这是RESTful设计的核心思想——用HTTP方法的语义来表达操作类型。

至于"GET参数在URL里，POST在body里"——这只是约定俗成，不是HTTP规范规定的。技术上GET也可以有请求体，POST也可以把参数放URL里，只是不推荐这么做，有些服务器/浏览器可能不支持。

### 5.3 什么时候用哪个？

简单原则：
- **获取数据** → GET（查列表、查详情、搜索）
- **新增数据** → POST（注册、下单、提交表单）
- **全量更新** → PUT（修改用户全部信息）
- **部分更新** → PATCH（只改个用户名）
- **删除数据** → DELETE（删除用户）

现实中很多团队为了省事，除了GET就是POST，也能干活。但规范一点总是好的——代码可读性更好，接口更清晰。

## 六、状态码详解：你必须知道的那些暗号

状态码太多了，不用全背，记高频的就行。

### 6.1 2xx成功

| 状态码 | 含义 | 说明 |
|--------|------|------|
| **200 OK** | 成功 | 最常见的，请求成功了 |
| **201 Created** | 创建成功 | POST创建资源成功 |
| **204 No Content** | 无内容 | 成功了，但没有返回数据（比如DELETE） |

### 6.2 3xx重定向

| 状态码 | 含义 | 说明 |
|--------|------|------|
| **301 Moved Permanently** | 永久重定向 | 网址搬家了，以后都去新地址 |
| **302 Found** | 临时重定向 | 暂时去别的地方 |
| **304 Not Modified** | 未修改 | 资源没变，用缓存就行（缓存相关） |
| 307 Temporary Redirect | 临时重定向 | 跟302类似，但不允许改请求方法 |
| 308 Permanent Redirect | 永久重定向 | 跟301类似，但不允许改请求方法 |

💡 **301 vs 302**：
- 301是永久的，浏览器会记住，下次直接访问新地址（SEO也会转移权重）
- 302是临时的，每次都先问老地址再跳转

### 6.3 4xx客户端错误

都是"你的问题"——请求不对。

| 状态码 | 含义 | 说明 |
|--------|------|------|
| **400 Bad Request** | 请求参数错误 | 参数不对、格式不对 |
| **401 Unauthorized** | 未授权 | 没登录/token无效 |
| **403 Forbidden** | 禁止访问 | 登录了但没权限 |
| **404 Not Found** | 找不到 | URL不对/资源不存在 |
| **405 Method Not Allowed** | 方法不允许 | 用了不支持的请求方法 |
| 408 Request Timeout | 请求超时 | 请求时间太长了 |
| 409 Conflict | 冲突 | 资源冲突（比如重复创建） |
| 413 Payload Too Large | 请求体太大 | 上传的东西太大了 |
| 429 Too Many Requests | 请求太多 | 被限流了 |

💡 **401 vs 403**：
- 401 = 你是谁？我不认识你（没登录）
- 403 = 我认识你，但你不能进（没权限）

### 6.4 5xx服务端错误

都是"服务器的问题"——后端崩了。

| 状态码 | 含义 | 说明 |
|--------|------|------|
| **500 Internal Server Error** | 服务器内部错误 | 后端代码崩了，最常见 |
| **502 Bad Gateway** | 网关错误 | 代理服务器（Nginx）没拿到后端响应 |
| **503 Service Unavailable** | 服务不可用 | 服务器挂了/过载了 |
| **504 Gateway Timeout** | 网关超时 | 代理等后端等太久了 |
| 501 Not Implemented | 未实现 | 服务器不支持这个功能 |

💡 **502 vs 504**：
- 502 = 后端挂了，Nginx连不上后端
- 504 = 后端太慢了，Nginx等不及超时了

### 6.5 高频状态码面试题

**Q：304是什么意思？什么情况下会出现？**
A：304是协商缓存的结果。浏览器第一次请求资源，服务器返回资源和ETag/Last-Modified；第二次请求时带上If-None-Match/If-Modified-Since，服务器判断资源没变，就返回304让浏览器用缓存。

**Q：401和403的区别？**
A：401是未认证（没登录/token无效），403是已认证但无权限（登录了但不能访问）。

**Q：500、502、503、504的区别？**
A：500是后端代码出错；502是网关连不上后端（后端挂了）；503是服务不可用（过载/维护）；504是网关超时（后端太慢）。

## 七、HTTP缓存：让网页飞起来

缓存是性能优化的大头。浏览器为什么第二次打开网页更快？就是因为缓存——很多资源不用重新下载。

HTTP缓存分两种：**强缓存**和**协商缓存**。

### 7.1 强缓存

**强缓存 = 浏览器直接用本地缓存，不跟服务器打招呼**。

怎么判断用不用强缓存？看这两个响应头：

| 响应头 | 作用 | 例子 |
|--------|------|------|
| `Cache-Control` | 缓存控制（HTTP/1.1） | `max-age=3600`（缓存3600秒） |
| `Expires` | 过期时间（HTTP/1.0） | 一个具体的GMT时间 |

Cache-Control的常用值：
- `max-age=3600` → 缓存3600秒
- `no-cache` → 不用强缓存，走协商缓存
- `no-store` → 完全不缓存
- `public` → 可以被任何代理缓存
- `private` → 只能被浏览器缓存

强缓存期间，浏览器直接从本地读文件，不会发请求——Network面板里会显示 `(from disk cache)` 或 `(from memory cache)`。

### 7.2 协商缓存

**协商缓存 = 浏览器先问服务器"资源变了吗？"，没变就用缓存，变了就重新下载。**

协商缓存有两对：

#### 第一对：Last-Modified / If-Modified-Since

```
第一次请求：
服务器响应 → Last-Modified: Wed, 21 Oct 2023 07:28:00 GMT
浏览器存下来

第二次请求：
浏览器请求 → If-Modified-Since: Wed, 21 Oct 2023 07:28:00 GMT
服务器判断：
  → 没改 → 返回 304 Not Modified（浏览器用缓存）
  → 改了 → 返回 200 + 新资源 + 新的Last-Modified
```

缺点：精度只能到秒，如果文件1秒内改了就检测不到。而且文件内容没变但修改时间变了也会重新传。

#### 第二对：ETag / If-None-Match

ETag就是资源的"指纹"——内容变了ETag就变。

```
第一次请求：
服务器响应 → ETag: "abc123"
浏览器存下来

第二次请求：
浏览器请求 → If-None-Match: "abc123"
服务器判断：
  → ETag一样 → 304（用缓存）
  → ETag不一样 → 200 + 新资源 + 新ETag
```

ETag比Last-Modified更精确，但生成ETag需要服务器计算，有一点性能开销。

💡 **实际项目中**：一般两个都会用，ETag优先。Cache-Control + ETag是标配。

### 7.3 缓存流程图

```
浏览器请求资源
     ↓
有缓存吗？——没有——→ 发请求 → 服务器返回资源 + 缓存策略 → 存缓存 → 用资源
     ↓ 有
强缓存过期了吗？——没过期——→ 直接用缓存（200 from cache）
     ↓ 过期了
发协商请求（带If-None-Match/If-Modified-Since）
     ↓
资源变了吗？——没变——→ 304 → 更新缓存时间 → 用缓存
     ↓ 变了
200 + 新资源 → 更新缓存 → 用新资源
```

记住这个流程，面试再也不怕缓存题了。

## 八、跨域：前后端联调第一痛

做前端的，谁没遇到过跨域？控制台红红的一片报错，看着就头疼。

### 8.1 什么是同源策略？

浏览器的安全策略：**协议、域名、端口，三者必须完全一样，才算同源**。不同源之间，默认不能互相请求资源、不能操作DOM。

| URL1 | URL2 | 是否同源 | 原因 |
|------|------|---------|------|
| http://a.com/a | http://a.com/b | ✅ 同源 | 协议域名端口都一样 |
| http://a.com | https://a.com | ❌ 不同源 | 协议不同 |
| http://a.com | http://b.com | ❌ 不同源 | 域名不同 |
| http://a.com:8080 | http://a.com:3000 | ❌ 不同源 | 端口不同 |
| http://www.a.com | http://api.a.com | ❌ 不同源 | 子域名不同 |

注意：跨域不是请求发不出去，请求是能发出去的，服务器也收到了也返回了，只是**浏览器把响应拦截了**——因为安全策略。

### 8.2 为什么会有跨域？

为了安全。如果没有同源策略，你打开一个恶意网站，它就能随便请求你银行网站的数据、读取你的Cookie……那不乱套了吗？

同源策略是浏览器最重要的安全基石之一。

### 8.3 常见跨域解决方案

#### 方案1：CORS（最常用、最推荐）

**CORS = Cross-Origin Resource Sharing（跨域资源共享）**——服务器在响应头里加几个字段，告诉浏览器"我允许这个域名跨域访问我"。

服务器加这些响应头：
```
Access-Control-Allow-Origin: https://example.com  // 允许的域名
Access-Control-Allow-Methods: GET, POST, PUT, DELETE  // 允许的方法
Access-Control-Allow-Headers: Content-Type, Authorization  // 允许的请求头
Access-Control-Allow-Credentials: true  // 允许带Cookie
```

💡 **预检请求**：跨域的非简单请求（比如Content-Type是application/json、带自定义头），浏览器会先发一个OPTIONS请求"探路"，服务器返回允许的头之后，才发真正的请求。这就是为什么你有时候会看到请求先发了一次OPTIONS。

CORS是后端配置的，前端不用做什么（除非要带Cookie，需要withCredentials）。

#### 方案2：开发环境代理（Vite/Webpack）

开发时用代理服务器转发请求，绕过浏览器的同源策略。

Vite配置：
```javascript
// vite.config.js
export default {
  server: {
    proxy: {
      '/api': {
        target: 'http://api.example.com',  // 后端地址
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, '')
      }
    }
  }
}
```

原理：浏览器请求 `/api/users` → Vite的dev server转发到 `http://api.example.com/users` → 后端返回 → Vite返回给浏览器

注意：这只在**开发环境**有用，生产环境还是要用CORS或者Nginx反向代理。

#### 方案3：Nginx反向代理

生产环境用Nginx做反向代理，把前端和后端放同一个域名下：

```nginx
server {
  listen 80;
  server_name example.com;
  
  # 前端页面
  location / {
    root /usr/share/nginx/html;
    index index.html;
  }
  
  # API接口转发到后端
  location /api/ {
    proxy_pass http://backend-server/;
  }
}
```

用户访问的都是 `example.com`，自然就没有跨域了。

#### 方案4：JSONP（老方法，基本不用了）

利用 `<script>` 标签不受同源策略限制的特点，动态创建script标签请求接口，后端返回一个函数调用的JS代码。

缺点：只能发GET请求，不支持POST/PUT等。现在基本被CORS取代了，了解一下就行。

👉 **总结**：
- 开发环境 → Vite代理
- 生产环境 → CORS 或 Nginx反向代理
- JSONP → 了解就行，基本不用了

## 九、HTTPS：为什么网址前面有个小锁？

你访问的网站，URL前面如果有个小锁🔒，就是HTTPS。没有的话，浏览器会标"不安全"。

### 9.1 HTTP的不安全

HTTP是明文传输的——你发的请求、服务器返回的响应，中间经过的路由器、运营商、WiFi，都能看到你传的是什么。

这就很危险了：
- 你登录账号，密码被中间人截获了
- 你看的网页，被运营商植入广告了
- 你转账的信息，被篡改了

HTTPS就是来解决这些问题的——加密传输，中间的人看不到也改不了。

### 9.2 HTTPS加密原理

HTTPS = HTTP + TLS/SSL（加密层）。

简单说一下加密过程（非对称加密 + 对称加密结合）：

1. **握手阶段（非对称加密）**：
   - 浏览器 → 服务器：我支持哪些加密方式
   - 服务器 → 浏览器：这是我的证书（含公钥），你验证一下
   - 浏览器验证证书合法 → 生成一个随机的"会话密钥"，用服务器的公钥加密发过去
   - 服务器用私钥解密，拿到会话密钥

2. **传输阶段（对称加密）**：
   - 双方都有了会话密钥，后面的数据都用这个密钥加密传输
   - 对称加密速度快，适合大数据量

为什么不全程用非对称加密？因为非对称加密太慢了，对称加密快。所以用非对称加密来"交换密钥"，然后用对称加密传数据。

### 9.3 HTTP vs HTTPS

| 对比项 | HTTP | HTTPS |
|--------|------|-------|
| 安全性 | 明文，不安全 | 加密，安全 |
| 端口 | 80 | 443 |
| 速度 | 快一点 | 略慢（加密有开销，但可以忽略） |
| 费用 | 免费 | 需要SSL证书（免费的也有，比如Let's Encrypt） |
| SEO | 权重低 | 权重高，搜索引擎优先 |
| 浏览器标识 | 标"不安全" | 小锁🔒 |

现在基本所有正规网站都是HTTPS了，HTTP的越来越少。做开发的时候，尽量全站HTTPS。

## 十、HTTP/2和HTTP/3：更快的协议

HTTP/1.1用了很多年，但它有一些问题：
- 同一域名下并发连接数有限（一般6个）
- 请求有队头阻塞（前面的请求慢，后面的都等着）
- 头部冗余，每次都带一大堆重复的头

### HTTP/2

HTTP/2解决了这些问题：
- **多路复用**：一个TCP连接可以并发发多个请求，不用等
- **头部压缩**：HPACK算法压缩请求头，减少传输量
- **服务器推送**：服务器可以主动给浏览器推资源
- **二进制格式**：用二进制传输，解析更快

### HTTP/3

HTTP/2还是基于TCP的，TCP本身有队头阻塞问题（一个包丢了，整个连接都等着）。

HTTP/3干脆不用TCP了，改用**QUIC协议**（基于UDP）：
- 没有队头阻塞
- 连接建立更快（0-RTT/1-RTT）
- 连接迁移（网络切换不中断，比如WiFi切流量）

现在很多大网站都已经支持HTTP/3了，未来的趋势。

## 十一、面试八股精选

HTTP是前端面试的重灾区，整理几道高频题：

### 1. 从输入URL到页面显示发生了什么？
**答题思路**：DNS解析 → TCP连接 → 发HTTP请求 → 服务器处理 → 返回响应 → 浏览器解析渲染 → 关闭连接。每个点展开说一两句，DOM树、CSSOM、渲染树、布局、绘制、合成。

### 2. GET和POST的区别？
**答题思路**：先说表面区别（参数位置、长度、安全性、缓存、幂等性），再说根本区别是语义不同——GET幂等（读），POST非幂等（写）。补充：GET也可以有body，只是不推荐。

### 3. 常见的状态码有哪些？
**答题思路**：分类说——2xx（200、201、204）、3xx（301、302、304）、4xx（400、401、403、404）、5xx（500、502、503、504），每个说1-2句含义。

### 4. HTTP缓存机制？
**答题思路**：强缓存（Cache-Control/Expires，不发请求直接用）+ 协商缓存（ETag/If-None-Match、Last-Modified/If-Modified-Since，发请求判断304还是200）。画个流程图更好。

### 5. 什么是跨域？怎么解决？
**答题思路**：同源策略（协议、域名、端口都相同）→ 为什么要有（安全）→ 解决方案：CORS（后端配响应头，预检请求）、开发代理（Vite/Webpack）、Nginx反向代理、JSONP（只支持GET，老方法）。

### 6. HTTPS的加密过程？
**答题思路**：非对称加密交换密钥 + 对称加密传输数据。握手阶段：客户端Hello → 服务器返回证书 → 客户端验证证书 → 生成会话密钥用公钥加密发给服务器 → 服务器用私钥解密。之后就用对称密钥加密通信。

### 7. 什么是Cookie？和Session、Token的区别？
**答题思路**：
- Cookie：浏览器存的小文件，每次请求自动带上，有大小限制（4KB）
- Session：存在服务器的会话，通过Cookie里的sessionId关联
- Token：令牌（比如JWT），服务器不存，自己验证签名
- 区别：存储位置、安全性、跨域支持、扩展性（分布式Session问题）

### 8. HTTP/2有什么新特性？
**答题思路**：多路复用（一个连接并发请求）、头部压缩（HPACK）、服务器推送、二进制格式、流量控制和优先级。

## 十二、总结与后续学习建议

### 12.1 本篇要点回顾

回顾一下这篇的核心内容：

1. **HTTP是什么**：超文本传输协议，浏览器和服务器通信的规则
2. **请求过程**：DNS解析 → TCP三次握手 → 发请求 → 服务器处理 → 返回响应 → 浏览器渲染
3. **请求报文**：请求行（方法+URL+版本）、请求头、空行、请求体
4. **响应报文**：状态行（版本+状态码+状态文本）、响应头、空行、响应体
5. **请求方法**：GET查、POST增、PUT改、DELETE删（RESTful）
6. **状态码**：2xx成功、3xx重定向、4xx客户端错、5xx服务端错
7. **HTTP缓存**：强缓存（Cache-Control）+ 协商缓存（ETag/Last-Modified）
8. **跨域**：同源策略 → CORS/代理/Nginx
9. **HTTPS**：HTTP + TLS加密，更安全
10. **HTTP/2和HTTP/3**：多路复用、更快的协议

### 12.2 学习心得

HTTP看着简单，其实水很深——缓存、跨域、安全、性能……每个点展开都能写一本书。

给前端新手的建议：
1. **先掌握常用的**：请求方法、状态码、请求头、响应头这些常用的先搞懂
2. **结合浏览器DevTools学**：打开Network面板，看每个请求的头信息，对照着学
3. **缓存和跨域是重点**：工作中经常遇到，面试也经常考
4. **不用死记硬背**：用的时候查文档，理解原理最重要

HTTP是前端的基本功，搞懂了HTTP，前后端联调的时候你就知道问题出在哪了，不会动不动就"后端的锅"。

🤖 **AI时代怎么学HTTP**：
- 遇到问题（比如跨域、缓存）直接问AI，AI会给你解决方案

- AI能帮你写代码、配代理，但排查网络问题还得靠你自己
- 面试的时候，HTTP的原理题AI帮不了你，得你自己答
